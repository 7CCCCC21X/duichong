## 1. 故障场景覆盖（对应需求第 9 条）

所有场景都在 `test/engine.test.ts` 中用模拟交易所驱动真实的引擎代码（同一套台账、补单、对账、风控逻辑），可控时钟、内存 SQLite。

| 需求场景 | 用例 | 结果 |
| --- | --- | --- |
| 部分成交 | 挂 50 份、实际成交 18 份：按新增 18 份补单，净敞口归零，挂单剩余 32 份 | 通过 |
| 部分成交（补单不足） | 补单只到账 12 份时，剩余 6 份继续管理直到对齐 | 通过 |
| 手续费扣份额 | Predict 补单按“净到账份额”倒推毛份额（多买以覆盖份额手续费），以结算回报的实际手续费为准 | 通过 |
| 重复与乱序事件 | 重复且乱序（先“结算成功”后“已撮合”）的推送只产生一次有效处理 | 通过 |
| 成交先于下单回执 | 成交推送先到、找不到本地订单时先暂存，订单拿到交易所 ID 后再匹配 | 通过 |
| 两边同时成交 | 两边各成交互补的 18 份时净敞口为零、不补单；锁定利润 18×(1−0.46−0.50)=0.72 | 通过 |
| 下单超时但实际成交 | 补单请求超时、推送也丢失：标记“状态未知”并按整笔预占，查单确认已成交后补拉成交，不重复补单 | 通过 |
| 撤单途中成交 | 撤单请求到达时先成交了 10 份：计入敞口并补单 | 通过 |
| 结算失败 | 补单已完成后才收到挂单成交结算失败：冲回后对冲腿多出，超过最长裸仓时间进入紧急处理，在亏损限制内处理 | 通过 |
| 结算失败（同时到达） | 撮合与结算失败在合并窗口内到达：直接冲回，不产生多余补单 | 通过 |
| 补单触发标准 | `hedgeTrigger=settled` 时结算成功前不补单 | 通过 |
| 断线重连 | 订单事件流断开：撤掉挂单并暂停；恢复并对账后重新挂单 | 通过 |
| 盘口断连 | 行情超过 `maxBookAgeMs` 未更新：撤掉挂单 | 通过 |
| 进程重启 | 停机期间挂单成交：重启后先对账补拉成交，不重复挂单，补完敞口 | 通过 |
| 进程重启（发送途中崩溃） | 本地 SENDING、交易所已受理：重启查单后接管该挂单 | 通过 |
| 重启对账 | 交易所持仓与台账不一致：暂停该配对挂单并告警 | 通过 |
| 深度消失 | 对冲盘深度消失：超过最长裸仓时间后撤挂单，比较“紧急补反向”与“卖回原腿”，选亏损最小且在限额内的方案 | 通过 |
| 余额不足（预留） | 补单平台只有 5 美元：按“预留全部挂单可能成交所需的补单资金”把挂单缩到约 9.5 份 | 通过 |
| 余额不足（拒单） | 挂单被拒（余额不足）：暂停该平台挂单并告警 | 通过 |
| 小额残余仓位 | 3 份残余低于 Polymarket 最小 5 份：先等待更多成交，超时后在 Predict 处理（市价卖最小 0.01 份） | 通过 |
| 小额残余（撤换空档） | 残余出现时挂单恰好在撤换重挂：仍然等待，不立即平仓（回归测试，修复前失败） | 通过 |
| 零头 | 低于 `dustShares` 的零头不处理 | 通过 |
| 对冲盘口恶化 | 挂价高于新的盈利上限：立即撤单 | 通过 |
| 停止挂单时间 | 到开赛前设定时间：撤单并停止挂单 | 通过 |

## 4. 真实公开行情核对（不需要凭证，`scripts/live-data-check.ts`）

2026-11-12 运行结果（Polymarket 主网公开接口 + Predict 测试网公开接口）：

- 选中 4 个未来 2~24 小时开赛的电竞整场胜负盘（CS2 / MLBB / LoL），均为 `v1`、费率 0.05、最小 5 份、tick 0.01。
- 订阅 8 个代币 45 秒，收到 104 次订单簿更新；**WebSocket 增量维护的订单簿与 REST 快照前 5 档逐档比对 8/8 一致**。
- 读到真实 CLOB 参数：撮合延迟 1000ms、开赛清簿 `true`。
- 真实深度下的补单成本示例（FURIA vs Vitality）：在 Polymarket 买 FURIA 10/50/200 份均价含费 0.3308（最差档 0.32），对应 Predict 买 Vitality 的盈利上限挂价 0.65；反方向为 0.7006 → 0.28。
- Predict 测试网 #437 Yes 簿买一 0.33 / 卖一 0.37，推导 No 簿买一 0.63 / 卖一 0.67。

配对发现（`node dist/cli.js pairs discover --all-types`，Predict 测试网 + Polymarket 主网）：
- 对测试网中带 `polymarketConditionIds` 的电竞子盘口逐个核对；测试网电竞副本都是已结算赛事，因此全部判为 REJECTED（原因：已开赛/已结算），规则一致的盘口结算情形矩阵全部为 1。
- 发现并修正了一个真实问题：Yes/No 盘“取消判 No”原先被误算为合计 0，改为比较两边兑付向量后判为一致（已加测试）。
- 实测 Predict 的 `providerTeamId` 等于 Polymarket 事件队伍的 `id`，已作为强匹配依据。

## 5. 端到端模拟交易（`scripts/paper-e2e.ts`）

对冲侧为**真实** Polymarket 盘口（真实 WebSocket 行情、按真实深度逐档成交、按真实费率计费）；Predict 挂单侧盘口为**合成数据**（没有 Predict 主网 API Key），用于驱动挂单与模拟成交。

| 步骤 | 结果 |
| --- | --- |
| 初始挂单 | 在 Predict 挂买 FURIA 0.28 × 50（auto 模式，盈利上限价） |
| 对手吃 18 份 | 在 Polymarket 以真实卖一 0.69 补 18 份 Vitality，手续费 0.19251（= 0.05×0.69×0.31×18，与官方公式一致），补单耗时约 285ms（含 180ms 模拟延迟与 100ms 合并窗口），净敞口 0 |
| 重复推送 7 份 | 只计一次，补 7 份 |
| 再成交 3 份（低于最小 5 份） | 进入 RESIDUAL_WAIT 等待 |
| 到停止挂单时间 | 撤挂单；不会再有成交，在 Predict 卖回 3 份残余，净敞口 0 |
| 汇总 | 已对冲 25 对，两腿净花费 24.53，费用 0.28，锁定费后盈亏 +0.47 |
